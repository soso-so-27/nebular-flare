## 1. IA（情報アーキテクチャ）/ 画面遷移図

### 1-1. タブ構成（確定版）

```
[ホーム]   [図鑑]   [📷撮影]   [うちの子]   [カレンダー]
  home    collection  camera      cat        calendar
```

- 5タブ固定。中央の撮影ボタンはアクセントカラーで強調
- 現行の `photo` / `notifications` / `zukan` タブは廃止し、上記に統一

### 1-4. グローバル遷移（どの画面からもアクセス可能）

```
全画面共通:
├── タブバー → 5タブ間の遷移
├── 撮影ボタン → CaptureWorkflowSheet
└── 通知 → NotificationSheet（ホーム右上からのみ）

認証切れ時:
└── どの画面からも → LoginScreen にリダイレクト
```

### 1-5. 廃止する遷移

| 旧遷移 | 理由 | 代替 |
|--------|------|------|
| `tab === "photo"` | ナビに存在しない | 図鑑タブの写真一覧 |
| `tab === "notifications"` | ナビに存在しない | ホームの通知ベル→シート |
| `tab === "zukan"` | 名前が不統一 | `collection` に統一 |
| `setTab("zukan")` (ImportWizard完了後) | 存在しないタブ | `home` に戻る |

### 2-3. 図鑑の成長メカニズム

```
collection_definitions (図鑑の軸)
  例: "ポーズ図鑑" / "季節の表情" / "お気に入りの場所"
        │
        ├── collection_rules (各軸のエントリ定義)
        │     例: "香箱座り" / "へそ天" / "窓辺"
        │

                    │
                    ▼

                ├── 初回マッチ → status: 'discovered' → discoveries に通知
                └── 追加写真 → cat_collection_photos に追加
                              → 代表写真の更新判定
```

## 3. コピーライティングガイド

### 3-1. トーンの定義

**にゃるほどの声は:**
- 猫好きの友達が話しているような、やさしくて自然な口調
- 機能の説明ではなく、猫との暮らしに寄り添う言葉
- 押し付けがましくない。静かに支える存在
- 「です/ます」は使うが、堅くなりすぎない

**にゃるほどの声ではないもの:**
- テック企業のマーケティングコピー
- 過剰にかわいい猫語（「にゃん」の多用など）
- 冷たい事務的な通知文
- AIの存在を誇示する表現

### 3-2. シーン別の文言ガイド

#### オンボーディング

```
✗ 「写真をアップロードしてAI分析を開始します」
✓ 「猫の写真を選んでください。この子の最初のアルバムを作ります」

✗ 「猫の情報を入力してください」
✓ 「あなたの猫のことを教えてください」

✗ 「セットアップが完了しました」
✓ 「準備できました。この子の物語、はじまります」
```

#### 写真インポート

```
✗ 「画像を解析中です」
✓ 「猫を見つけています...」

✗ 「分類が完了しました」
✓ 「見つけました！ 麦くんが3枚、雨くんが2枚」

✗ 「5件のエラーが発生しました」
✓ 「5枚の写真はうまく読み込めませんでした。あとからもう一度試せます」
```

#### 図鑑 / 発見

```
✗ 「新しいタグが検出されました」
✓ 「新しい発見！ 麦くんの "へそ天" を初めて見つけました」

✗ 「コレクション進捗: 60%」
✓ 「ポーズ図鑑: あと4つで完成！」

✗ 「データがありません」
✓ 「まだ写真がありません。撮ってみましょう」
```

#### 通知

```
✗ 「週次レポートが生成されました」
✓ 「今週のアルバムができました」

✗ 「1年前のデータが見つかりました」
✓ 「1年前の今日、麦くんはこんな顔をしていました」

✗ 「ケアタスクのリマインダー」
✓ 「雨くんのごはんの時間です」
```

#### エラー / 空状態

```
✗ 「Error: Network request failed」
✓ 「つながりにくいようです。しばらくしてからまた開いてみてください」

✗ 「データが見つかりません」
✓ 「まだ何もありません」

✗ 「ログインセッションが切れました。再認証してください」
✓ 「もう一度ログインしてください」
```

### 3-3. 用語統一表

| 内部用語 / 技術用語 | アプリ内表現 |
|---|---|
| photo upload | 写真を追加 |
| AI analysis | （表示しない。結果だけ見せる） |
| collection | 図鑑 / コレクション |
| discovery | 発見 |
| care_log | ケア記録 |
| incident | できごと |
| household | 家族 |
| sync | （使わない） |
| export | 写真をまとめて保存 |
| subscription / premium | にゃるほど プラス |
| notification | おしらせ |
| settings | 設定 |
| onboarding | （表示しない。自然な流れで誘導） |
| delete | 削除する / 取り消す |
| archive | しまう |

### 3-4. 数字の表示

```
日付:  「3月21日（金）」 ← 曜日あり、年は省略（同年内）
       「2025年3月21日」 ← 年が異なる場合
時刻:  「14:30」 ← 24時間表記
期間:  「3日前」「先週」「1年前の今日」 ← 相対表記を優先
枚数:  「12枚」 ← 「12 photos」ではなく
体重:  「4.2 kg」 ← 単位は半角スペース + kg
```

## 4. アナリティクス設計

### 4-1. 計測の目的

事業性分析で定義した Go/No-Go 判断に必要なデータを収集する。
過剰な計測は行わない。意思決定に直結する指標だけ。

### 4-2. コア指標（North Star Metrics）

| 指標 | 定義 | 目標 | 計測方法 |
|------|------|------|---------|
| **WAU** (Weekly Active Users) | 週に1回以上アプリを開いたユーザー数 | Phase 1: 30人 | Supabase auth logs |
| **週間写真追加数/ユーザー** | 1ユーザーが1週間に追加した写真数 | 5枚以上 | photos テーブル |
| **図鑑エンゲージメント** | 図鑑を開いたユーザーの割合 | WAUの50% | イベントログ |
| **継続率（1週間）** | 登録後1週間以内に再訪したユーザー | 40% | auth + イベント |
| **継続率（1ヶ月）** | 登録後1ヶ月以内に再訪したユーザー | 20% | auth + イベント |

### 4-3. ファネル指標

```
登録 → オンボーディング完了 → 初回写真追加 → 初回図鑑生成 → 1週間後再訪
  │          │                    │                │              │
  └── 離脱率A  └── 離脱率B          └── 離脱率C      └── 離脱率D    └── 継続率
```

各ステップの離脱率を計測し、最もボトルネックになっている箇所を改善する。

### 4-5. 実装方針

- Phase 1 では **Supabase テーブルへの直接ログ** で十分（外部ツール不要）
- `analytics_events` テーブルを作成し、上記イベントをINSERT
- Phase 2 以降でFirebase Analytics等への移行を検討
- **個人を特定できる情報はログに含めない**（user_id のみ、写真内容は含めない）

```sql
CREATE TABLE analytics_events (
  id uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id uuid REFERENCES auth.users(id),
  event_name text NOT NULL,
  params jsonb DEFAULT '{}',
  created_at timestamptz DEFAULT now()
);
```
